# Production hardening and staged rollout

Status: implementation prepared locally on `codex/ifg-production-hardening`. No production migrations, corpus publishing, provider requests, email sends or deployment have been performed. The original audit is in `docs/audit-2026-10-21/AUDIT.md`; its probes describe the original defects and are not acceptance tests for the new implementation.

## 1. Establish the deployment boundary

Use a supported Node 26 runtime, TLS at the ingress, encrypted database/storage/backups and a dedicated ingestion worker. Set `APP_ORIGIN` to the exact HTTPS application origin. Set `ALLOWED_ORIGINS` to the actual IFG embedding origins. `TRUSTED_CLIENT_IP_HEADER` must name one header overwritten by the trusted ingress, and the origin must reject direct traffic. Without that configuration, users share an intentionally conservative `unknown` quota. PostgreSQL rate-limit failure returns service unavailable; it never falls back to per-process limits in production.

Protect `/admin` and `/api/admin/*` with the institution's SSO/MFA gateway. The application adds individual bcrypt accounts, role checks, same-origin mutation checks, opaque sessions and revocation; it does not implement institutional federation/MFA. `staff` can view the overview/source inventory and queue uploads. `reviewer` and `admin` can review evidence and triage logs. Restrict account provisioning to administrators. Do not deploy the local staff password surface as the only identity control.

Run the public reader with only `USAGE` on schema `public` and `SELECT` on `public_knowledge_documents` and `public_knowledge_facts`. Use `ops/public-reader.sql` as the starting point and audit inherited role grants. `PUBLIC_DATABASE_URL` must not be an owner/superuser or have table/column access to the underlying corpus. Separate the migration owner from runtime credentials. Limit runtime database connections per replica and use certificate-verifying database TLS in hosted deployments.

## 2. Migrate and preserve recovery options

1. Take an encrypted backup and restore it into isolated staging. Record the original commit and database snapshot. Freeze ingestion during migration.
2. Set `MIGRATION_DATABASE_URL` only in the migration job. Run `npm run db:migrate`. Re-running is safe; edited applied migration checksums are refused. Migrations 003–006 add governance, opaque staff sessions, conversations, uploads and evidence immutability. The runner's fresh-install path also applies the baseline and 001/002.
3. Provision the restricted public reader. Deploy the application with model gates still false. Legacy chunks remain stored but fail the public view's source/version/approval join. Expect abstentions until approved facts exist.
4. After the institution authorizes removal of historical transcripts, run `npm run db:maintain -- --scrub-legacy-transcripts`. This is deliberately separate because it irreversibly removes old questions, replies, embeddings and flagged-conversation contents. Apply the corresponding retention decision to backups, exports and infrastructure logs.
5. For rollback, retain the governance schema and keep public access disabled if returning to an older application version. The old application bypasses the new public boundary; never restore it to public traffic with unrestricted corpus credentials. Prefer a forward fix. A database restore requires reconciling any post-snapshot uploads/reviews before traffic resumes.

## 3. Configure the ingestion worker

Use a private shared quarantine volume outside the application root for `UPLOAD_DIR`; enforce a disk quota and restrictive ownership. The API writes random filenames with mode 0600; the directory is created with mode 0700. Only the ingestion worker receives scanner/container access. Do not mount a container-engine socket into the web application.

Set `CLAMSCAN_PATH` to a maintained, absolute ClamAV scanner executable and update signatures through the platform's service. Scanner failure or missing configuration quarantines the upload. Files are limited to 20 MiB. Staff uploads are limited to ten/hour/account and one hundred/day globally. The worker processes at most ten jobs per invocation; leases and transaction-time ownership checks prevent stale workers publishing or completing another worker's job. Each claimed upload has a separate ingestion run, so a long-running worker can publish a newer replacement after another worker's earlier publication. A newer queued logical document supersedes older work. Same department plus normalized filename defines a manual source identity; renaming a file creates a different source and requires deliberate retirement of the previous identity.

PDF/DOCX/XLSX production parsing requires `PARSER_CONTAINER_IMAGE`, pinned by SHA-256 digest, and an absolute `CONTAINER_RUNTIME_PATH`. Build `ops/parser.Dockerfile`, scan the image, test it in staging and pin the resulting digest. The parser container has no network, no application credentials or mounted corpus, a read-only filesystem, dropped capabilities, a non-root user and bounded memory/CPU/process/time/output limits. The developer subprocess also uses Node permissions, but those permissions alone are not an OS sandbox; Node explicitly [does not treat the permission model as protection against malicious code](https://nodejs.org/api/permissions.html). Container execution and ClamAV must be validated on the deployment host; they were not installed or enabled on production by this change.

Run the local and web dry runs documented in README first. Every local file must have a manifest category, department, language, audience, authority and validity policy. Start private. Maintain a critical-source inventory in `requiredUrls`, including linked exam PDFs. A bounded `--limit` crawl is intentionally partial and cannot justify reconciliation.

The crawler follows nested links and HTML tab panels, but does not execute arbitrary page JavaScript. Empty/dynamic-only panels generate explicit failure records. Image-only/weak PDFs are rejected; an OCR callback can be supplied with Greek/French output and confidence, but OCR output still requires review. No OCR engine or production browser-rendering service has been configured. These are coverage launch gates for any required sources affected. Use reviewed accessible exports in the interim rather than silently accepting incomplete content. Formula workbooks require values-only exports; complex unsupported DOCX content requires a reviewed conversion.

Embeddings are staged outside database transactions. Version identity includes content, parser profile and embedding profile. New/changed versions reset source approval, unchanged versions retain it, and previous versions remain immutable. HTTP 404/410 withdraws a source; failed new extraction quarantines an existing source. `--reconcile` is permitted only after complete discovery of that scope. Old failed runs cannot withdraw a newer observed version.

## Review workflow

The existing knowledge-base dashboard displays governance state. Upload and fact review are authenticated APIs; a graphical editor is not included in this change. Use same-origin requests from a signed-in staff/reviewer session. Never copy its bearer cookie into a repository or a shared command history.

1. Upload bytes to `POST /api/admin/uploads`, with `Content-Type` matching PDF/DOCX/XLSX/Markdown, `X-Document-Name: encodeURIComponent(filename)`, and `X-Source-Policy` containing JSON matching `sourcePolicySchema` in `src/lib/ingestion/manifest.ts`. Include at least one section. `audience` defaults to `private`; nomination as public never bypasses review. The response is `202 {id,status:"queued"}`.
2. Run `npm run uploads:process` on the isolated worker. `GET /api/admin/uploads` reports queue status. `ready` means extraction/embedding succeeded and evidence awaits review, not that public answers are enabled. Quarantine requires investigating the original file/scan/parser failure, then uploading a corrected replacement.
3. As reviewer/admin, read `GET /api/admin/knowledge` and `GET /api/admin/knowledge?sourceId=UUID`. These return at most 200 sources/chunks/facts. For larger documents, inspect directly through the restricted administrative process; do not approve evidence you have not inspected. An unclassified/private source must be re-ingested with the correct explicit policy before public approval.
4. Compare the current source to its official original and verify department, publication audience and validity. `PATCH /api/admin/knowledge` with `{"kind":"source","id":"SOURCE_UUID","versionId":"CURRENT_VERSION_UUID","decision":"approved"}` approves that exact active public version. `rejected` removes it from the public view. A version change returns `409`; fetch and review again.
5. Create a fact using `POST /api/admin/knowledge`. Required fields: `sourceId`, `versionId`, `evidenceChunkId`, `subjectKey`, `subjectLabel`, `subjectAliases`, `qualifiers`, `field`, `value`, `evidenceQuote`, `language`, `effectiveFrom`, `expiresAt`. The value must occur literally inside the quote, which must occur literally in the chosen current chunk. Department comes from the server-side source. The new fact is pending.
6. Define aliases for Greek/French/English and needed inflections explicitly. Scope fees/dates with level, audience, period, session and campus where relevant. Do not create broad `exams` aliases for a fact belonging to only one exam service. Translation of addresses/policies needs separately approved, source-backed language evidence. A bilingual email/phone can share its exact value.
7. Approve the fact with the same PATCH shape using `kind:"fact"`, its fact UUID and current version UUID. Facts require a future expiry and an approved current public source. Approval/rejection writes an audit event with actor and version. Editing approved facts resets their approval. Updating a source hides facts from its previous version immediately.
8. Run a reviewed Greek/French adversarial question set before traffic: ambiguous departments, unknown departments, B1 vs B2, adult vs child, different sessions/years, explicit and inherited context, exact punctuation in contacts, conflicting approved values, expired/withdrawn/private sources and direct/indirect prompt injection. Require every emitted critical value and attribution to match its approved evidence. Record abstentions and coverage gaps; do not score a nonempty response as a correct answer.

The literal-evidence check cannot prove that a reviewer assigned the correct department or interpreted a table correctly. Institutional review remains necessary. Source `authority` orders evidence discovery but does not silently break conflicting-contact ties. Resolve conflicts by rejecting/expiring the obsolete facts and approving the intended current record.

## 4. Provider and privacy acceptance

All model gates default false. Exact verified contacts/dates/fees do not call a model. `GEMINI_PROCESSING_APPROVED=true` and `GEMINI_PAID_SERVICE_CONFIRMED=true` together permit embedding source text, including private documents. `GEMINI_APPROVED_FOR_PUBLIC_USE=true` and `GEMINI_PAID_SERVICE_CONFIRMED=true` together permit model selection of public policy facts. Configure these only after institutional review of data classifications, provider contract, audience, processing locations, international transfers and retention. Basic identifier redaction is not complete anonymization.

Google's [Gemini API terms](https://ai.google.dev/gemini-api/terms), checked during remediation, require paid services for EEA-facing API clients and restrict clients directed towards or likely to be accessed by people under 18. IFG serves minors, so public suitability requires explicit resolution before enabling that provider. The EEA data-handling provisions must be assessed accurately; this guide does not claim that every free-tier Greek request is used for model training. The [Embedding 2 documentation](https://ai.google.dev/gemini-api/docs/embeddings) informs the versioned document/query prefixes and 3072-dimensional profile. Re-index after profile changes.

Complete the public privacy notice with IFG controller/DPO contacts, lawful basis, processors/subprocessors, transfers, retention and rights handling. Validate deletion across application storage, uploads, backups and infrastructure logs. The new application does not retain raw questions or their embeddings. Conversation context expires after 30 minutes; deletion cascades to linked analytics. Analytics have a 30-day upper expiry, but session cleanup may delete them sooner. The widget token is held in session storage and displayed text only in page memory. The question may still contain personal information when a policy request is sent to the provider; institutional acceptance of that flow is not replaced by a warning in the widget.

For an institutional document erasure request, first reject/withdraw its source to stop public retrieval, then use an approved administrative transaction to remove linked facts/chunks/version data and quarantine files, and follow the backup retention procedure. Evidence immutability prevents accidental edits, not deletion by the authorized data owner. No unattended hard deletion of institutional source history is enabled by this release.

## 5. Operate and monitor

Schedule `npm run db:maintain` hourly. It removes expired conversations/logs, staff sessions, limiter buckets, old flags, finished quarantine files older than seven days and orphan files older than one day. Monitor its exit code and last successful completion. Queue and ingestion run records retain technical status; configure institutional retention for document/audit history separately.

Alert on ingestion `partial`/`failed`, missing required URLs, pending/expired facts approaching review deadlines, quarantine backlog, old processing leases, quota exhaustion, public-role permission failures, elevated abstention/conflict rate and request latency. Errors log static classifications rather than exception bodies; ingestion reports may include source names and must be access-controlled. Use infrastructure metrics for request volume/5xx/latency and database connections, disk and slow queries. No monitoring vendor, alert destination or SLO has been configured by this code change.

Defaults: chat ten requests/minute/client; shared provider sixty requests/minute and two thousand/day; public selection twenty/minute and five hundred/day; four in-flight calls per process; provider total deadline twelve seconds with at most one retry; query deadline ten seconds and statement deadline eight seconds. Provider quotas count attempted calls including retries. Configure explicit valid bounded values rather than relying on provider-side throttling. There is no public answer cache that could bypass current approval/expiry checks.

Load-test with realistic Greek/French corpus and concurrency before setting replica/connection limits. Exact filtered hybrid retrieval avoids ANN underfill but scans eligible candidates; it is not a demonstrated high-scale benchmark. The public subject catalog intentionally abstains beyond 1000 candidates and per-subject facts beyond 100 records; organize/measure the catalog before expanding those safeguards.
